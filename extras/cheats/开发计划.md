# 屏幕直播 & RTSP 摄像头转发系统 · 服务端/客户端开发计划

> 技术主线：服务端 ZLMediaKit（多协议收发/转封装）｜客户端 Qt/QML + libav*（MSVC 共用库）｜浏览器 WebRTC 拉流（最低延迟）

---

## 一、总体架构与边界

链路A（摄像头）： RTSP Camera ──rtsp──▶ ZLMediaKit(addStreamProxy按需拉流) ──WebRTC/FLV/HLS──▶ 浏览器
链路B（本机直播）：Windows 屏幕+麦克风 ──libav*采集编码──▶ RTMP推流 ──▶ ZLMediaKit ──WebRTC/FLV/HLS──▶ 浏览器

ZLMediaKit 的核心工作方式是"**一种协议推入、任意协议播出**"：内部把流统一为 MediaSource（schema+vhost+app+stream 四元组），同一份数据可同时以 rtmp/rtsp/hls/http-flv/webrtc 多种 schema 按需分发<span data-allow-html class="search-source-placeholder" data-keys="turn0search13" data-label="zhuanlan.zhihu.com"><span class="search-source-item-label"><a data-allow-html href="https://zhuanlan.zhihu.com/p/2085659134314264117" target="_blank" rel="noopener noreferrer">zhuanlan.zhihu.com</a></span><span class="source-item-num-count"></span></span>。这决定了两条链路可以共用同一台服务器、同一套鉴权与运维体系。

**开发顺序原则**：服务端先行（先让流能进出），客户端随后（往服务器里推），浏览器端最后统一接入。总工期预估 **服务端 3 周 + 客户端 4 周 + 联调 2 周 ≈ 9 周**。

### S0 环境搭建

用官方 Docker 镜像一条命令起服务，端口规划如下<span data-allow-html class="search-source-placeholder" data-keys="turn0search6,turn0search8" data-label="vcloud.csdn.net +1"><span class="search-source-item-label"><a data-allow-html href="https://vcloud.csdn.net/6ab4f9e905257b085712dd35.html" target="_blank" rel="noopener noreferrer">vcloud.csdn.net</a></span><span class="source-item-num-count"> +1</span></span>：

```bash
docker run -id --name zlm \
  -p 1935:1935 -p 8554:554 -p 8080:80 -p 8443:443 \
  -p 10000:10000 -p 10000:10000/udp \
  -p 8000:8000/udp -p 9000:9000/udp \
  -v ./conf:/opt/media/conf -v ./data:/opt/media/bin/data \
  zlmediakit/zlmediakit:master
```

| 端口     | 协议    | 用途                       |
| -------- | ------- | -------------------------- |
| 1935     | RTMP    | 客户端推流（链路B入口）    |
| 8554→554 | RTSP    | 摄像头接入/RTSP 播出       |
| 8080→80  | HTTP    | REST API、播放页、HTTP-FLV |
| 8443→443 | HTTPS   | WHEP 信令（需配证书）      |
| 8000/udp | WebRTC  | 媒体传输                   |
| 10000    | TCP/UDP | RTP 代理/GB28181 预留      |



**关键配置**（`config.ini` 挂载到宿主机，便于版本管理）：

- `[api] secret=`：REST API 密钥，生产环境必须用 `uuidgen` 生成并定期轮换，否则 `addStreamProxy` 这类危险接口可被任意调用[blog.csdn.net](https://blog.csdn.net/gitblog_00402/article/details/151528701)。
- `[rtc] externIP=`：**公网部署必填服务器公网 IP**，这是 WebRTC 能不能播出来的第一决定项[blog.csdn.net](https://blog.csdn.net/agile9scrum/article/details/155117096)。

**验收标准**：`docker ps` 服务存活；访问 `http://IP:8080/index/api/getServerConfig?secret=xxx` 返回 JSON；FFmpeg 推一路测试流 `ffmpeg -re -i test.mp4 -c copy -f flv rtmp://IP:1935/live/demo` 后，`getMediaList` 能查到该流及其多协议播放地址[vcloud.csdn.net](https://vcloud.csdn.net/6ab4f9e905257b085712dd35.html)。

### S1 RTSP 摄像头接入（链路A）

用 REST API 动态添加拉流代理，而不是写死在配置文件里[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/restful_api.html)+1：

Text



```
        POST /index/api/addStreamProxyvhost=__defaultVhost__&app=camera&stream=cam_001&url=rtsp://admin:pwd@192.168.1.64:554/Streaming/Channels/101&retry_count=-1            # 断线无限重试&rtp_type=0                # 0=TCP 拉流（摄像头链路建议 TCP）
      
```

同时实现**按需拉流**：配置 `on_stream_not_found` Hook，播放请求到达但流不存在时，业务服务调 `addStreamProxy` 即时拉起；配置 `on_stream_none_reader`，无人观看时自动关闭源站连接，节省摄像头带宽[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/web_hook_api.html)+1。

**验收标准**：调 `addStreamProxy` 后，浏览器访问 `http://IP:8080/camera/cam_001.live.flv` 能看到摄像头画面；HLS 地址 `/camera/cam_001/hls.m3u8` 同样可播（ZLMediaKit 的播放 URL 规则见官方文档）[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/play_url_rules.html)；拔掉摄像头网络，`retry_count=-1` 生效自动重连。

### S2 推流鉴权与安全

启用 Web Hook 做动态鉴权，这是 ZLMediaKit 权限体系的灵魂[blog.csdn.net](https://blog.csdn.net/gitblog_00402/article/details/151528701)+1：

ini



```
        1[hook]2enable=13admin_params=secret=<uuid>     # 仅调试用，生产关闭4on_publish=http://业务服务/zlm/hook/on_publish   # 推流鉴权（客户端推流令牌校验）5on_play=http://业务服务/zlm/hook/on_play         # 播放鉴权（浏览器观看令牌校验）6on_stream_changed=http://业务服务/zlm/hook/on_stream_changed  # 流上下线事件
      
```

鉴权逻辑在业务侧实现：Hook 收到 POST 后校验 params 里的 token，返回 200 放行、403 拒绝。配套 `[http] allow_ip_range=` 做 IP 白名单的网络层防护[blog.csdn.net](https://blog.csdn.net/gitblog_00402/article/details/151528701)。

**验收标准**：无 token 推流被拒（返回 403）；带 token 可推可播；`on_stream_changed` 事件能在业务侧正确记录流状态。

### S3 WebRTC 浏览器播放

ZLMediaKit 内置完整 WebRTC 信令（SDP 协商 + DTLS 握手），推 RTMP 进来即可直接 WebRTC 播出，无需额外信令服务[vcloud.csdn.net](https://vcloud.csdn.net/6ab4f4b5ad85947e68cc030e.html)+1。实测局域网端到端延迟约 **300–500ms**，远低于 HLS 的 5–10s[vcloud.csdn.net](https://vcloud.csdn.net/6ab4f4b5ad85947e68cc030e.html)。

落地要点：

1. `[rtc] externIP` 正确（外网必填公网 IP）[blog.csdn.net](https://blog.csdn.net/agile9scrum/article/details/155117096)
2. 防火墙/安全组放行 **8000/udp**（WebRTC 媒体）与 **443/tcp**（WHEP 信令）[blog.csdn.net](https://blog.csdn.net/qq_43750686/article/details/146062239)
3. HTTPS 下才能用浏览器的 `getUserMedia` 等能力；纯播放场景 WHEP 信令走 HTTP 也可用
4. 播放页可直接用 ZLMediaKit 自带的 `webrtc/` 演示页验证，业务页面后续自建[juejin.cn](https://juejin.cn/post/7675246437878775823)

**验收标准**：Chrome 打开 WebRTC 播放页，输入流地址后 3 秒内出画面；局域网实测端到端延迟 < 500ms；同时开 5 路播放不掉帧。

### S4 运维与扩展

- **监控**：`getMediaList`/`on_flow_report` Hook 接入流量统计，做带宽监控与计费基础[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/web_hook_api.html)
- **录制**：ZLMediaKit 支持 MP4 录制（`on_record_mp4` Hook），可为直播留存回放[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/web_hook_api.html)
- **扩容预案**：单机带宽到顶后走 CDN 分发（HLS/HTTP-FLV 天然可 CDN）或多实例横向扩容（WebRTC 场景按流哈希分片）；这个预案先文档化，本期不实现
- 生产暴露检查：secret 保管、HTTPS/反代、防火墙只开必要端口[juejin.cn](https://juejin.cn/post/7675246437878775823)

## 三、客户端开发计划（Qt/QML + libav*，MSVC）

前提：**沿用现有项目的 libav\* 动态库**（dll + import lib + headers 统一一套），所有新模块编译时指向同一套库，避免 MSVC 下多版本混链。

### 阶段总览

| 阶段                     | 周期      | 核心任务                     | 交付物                 |
| ------------------------ | --------- | ---------------------------- | ---------------------- |
| C0 libav* 集成           | 第4周前半 | 库路径接入 CMake、运行时对齐 | 工程能调 libav API     |
| C1 采集模块              | 第4周后半 | 屏幕 + 麦克风采集封装        | QML 可枚举设备并取到帧 |
| C2 编码与推流            | 第5周     | x264+aac 编码、RTMP 推流     | 完整链路B客户端        |
| C3 RTSP 摄像头客户端链路 | 第6周前半 | 拉流转发或直接调服务端 API   | 链路A客户端入口        |
| C4 QML UI 与状态机       | 第6周后半 | Streamer 类、推流控制界面    | 可操作的产品雏形       |
| C5 稳定性                | 第7周     | 断流重连、崩溃恢复、降级     | 达到联调标准的客户端   |



### C0 libav* 集成（工程骨架）

CMakeLists 核心段：

cmake



```
        1set(FFMPEG_ROOT "path/to/你现有库目录")2target_include_directories(streamer PRIVATE ${FFMPEG_ROOT}/include)3target_link_directories(streamer PRIVATE ${FFMPEG_ROOT}/lib)4target_link_libraries(streamer avcodec avformat avutil avdevice swresample swscale)5# 运行时：部署脚本把 ${FFMPEG_ROOT}/bin/*.dll 拷到输出目录，或加 PATH
      
```

**注意运行时统一 `/MD`**：若现有库是 `/MD` 构建的动态库，Qt 侧保持一致即可；避免引入 vcpkg `x64-windows-static`（`/MT`）造成 RuntimeLibrary 冲突。**架构参考直接对齐 OBS Studio 的 `obs-outputs` 插件**——它是 libavformat 做 FLV/RTMP 封装推流的生产级范本【turn4search0】。

**验收标准**：一个最小 demo 能 `avformat_open_input` 打开本地 mp4 并读出流信息，证明库链路可用。

### C1 采集模块

- 屏幕：`avdevice` + dshow（screen-capture-recorder，支持窗口/区域采集）或 gdigrab 思路的等价封装[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/web_hook_api.html)
- 麦克音/系统声：`avdevice` 枚举 dshow 音频设备（先 `avdevice_list_devices` 让 QML 下拉选设备）[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/web_hook_api.html)
- 封装为 `ScreenAudioCapturer` 类：`QList<Device> enumerate()` + `start(Device)` + `frameAvailable(AVFrame*)` 信号

**验收标准**：QML 页面能列出设备清单；启动采集后能连续取到 AVFrame（校验 PTS 单调、分辨率正确）。

### C2 编码与推流（链路B核心）

- 视频编码：`avcodec_send_frame` + libx264，参数对齐直播标准：`preset=ultrafast, tune=zerolatency, g=50, no-scenecut, pix_fmt=yuv420p, bitrate≈2.5Mbps(1080p)`
- 音频编码：AAC 44.1k 128k
- 封装推流：`avformat_alloc_output_context2(&fmt, NULL, "flv", "rtmp://...")`，写 header → 循环写 packet → close；音视频用各自 time_base 正确换算（这块照抄 OBS obs-outputs 的实现思路）
- 推流地址：`rtmp://服务器IP:1935/live/screen_<clientId>?token=<S2 签发的令牌>`

**验收标准**：客户端推流 5 分钟不丢帧；服务器 `getMediaList` 可见该流；浏览器 HTTP-FLV 播放延迟 <2s、WebRTC 播放延迟 <500ms。

### C3 RTSP 摄像头客户端链路

客户端侧不重做拉流转发（服务器已用 `addStreamProxy` 处理），而是实现**管理界面**：QML 里配置摄像头 RTSP 地址 → 调 ZLMediaKit REST API 注册为 StreamProxy → 展示服务器返回的多协议播放地址。若个别摄像头需要本地转码（如 H.265→H.264），客户端加一个可选的 libav* 转码推流通道，复用 C2 管线。

**验收标准**：从客户端 UI 添加一台摄像头，10 秒内浏览器可见画面，全程无需登录服务器。

### C4 QML UI 与状态机

- `Streamer` 类暴露给 QML：`start(config) / stop() / state / error / stats`（帧率、码率、已推时长）
- 状态机：`Idle → Connecting → Streaming → Retrying → Error`，所有状态迁移发 `stateChanged` 信号供 QML 渲染
- 采集/编码/推流分三个 QThread，用 `AVFrame` 队列解耦，队列超限自动丢帧防内存膨胀

**验收标准**：QML 界面完成一次完整的"选设备 → 开始推流 → 观看验证 → 停止"闭环操作。

### C5 稳定性

- 断流重连：网络抖动/服务器重启后自动重推，指数退避，上限 5 次
- 崩溃隔离：采集/编码线程 panic 不拖垮 UI（信号槽跨线程 + try-catch 包裹）
- 降级策略：带宽不足时自动降码率/降分辨率（阶梯 1080p→720p→540p）

**验收标准**：拔网线 10s 再插上，客户端自动恢复推流；持续推流 24 小时内存无泄漏（任务管理器观察 + heap 快照对比）。

## 四、浏览器端（并入 S3 与联调阶段）

自建播放页，二选一起步：

- **WebRTC（WHEP）**：`RTCPeerConnection` + fetch POST 到 ZLMediaKit 的 WHEP 端点，延迟 300–500ms，互动场景首选[vcloud.csdn.net](https://vcloud.csdn.net/6ab4f4b5ad85947e68cc030e.html)+1
- **HTTP-FLV**：`flv.js`（MSE）播放 `http://IP:8080/live/xxx.live.flv`，延迟 1–2s，兼容性好[docs.zlmediakit.com](https://docs.zlmediakit.com/guide/media_server/play_url_rules.html)

页面携带 S2 签发的播放 token，走 `on_play` 鉴权。

## 六、风险清单与规避

| 风险                     | 影响                          | 规避                                                         |
| ------------------------ | ----------------------------- | ------------------------------------------------------------ |
| WebRTC `externIP` 配错   | 浏览器一直 connecting，最大坑 | 部署脚本强制校验该字段；外网必填公网 IP[blog.csdn.net](https://blog.csdn.net/agile9scrum/article/details/155117096) |
| UDP 8000 被防火墙拦      | WebRTC 无画面                 | 云安全组 + iptables 提前放行；排错先查这里[blog.csdn.net](https://blog.csdn.net/qq_43750686/article/details/146062239) |
| RTSP 摄像头是 H.265      | 浏览器 WebRTC 解不出（黑屏）  | 优先让摄像头出 H.264；否则客户端/服务器侧加转码[github.com](https://github.com/ZLMediaKit/ZLMediaKit/issues/2503) |
| MSVC + libav* 运行时冲突 | 链接期报 RuntimeLibrary 错误  | 全项目统一 `/MD` 动态库；禁用 vcpkg static triplet           |
| `api secret` 泄露        | addStreamProxy 被恶意调用     | uuidgen 生成、定期轮换、127.0.0.1 白名单[blog.csdn.net](https://blog.csdn.net/gitblog_00402/article/details/151528701) |
| Hook 超时（504）         | 推拉流被误拒                  | `timeoutSec` 给足、业务侧异步处理鉴权[www.hqwc.cn](https://www.hqwc.cn/a/1156579.html) |
| 音视频时间戳漂移         | 长时间直播音画不同步          | 编码侧统一时钟基准、定期校正 PTS                             |



## 七、验收标准汇总（Checklist）

- [ ] 摄像头流：浏览器 WebRTC 播放，延迟 <500ms，断网自动恢复
- [ ] 屏幕直播：Qt 客户端推流，浏览器观看，延迟 <500ms（WebRTC）/ <2s（FLV）
- [ ] 推流/播放均需 token 鉴权，无 token 拒绝
- [ ] 客户端连续推流 24h 无内存泄漏、无崩溃
- [ ] 10 路并发观看下服务器 CPU <70%、带宽可预期
- [ ] 部署文档 + 一键 compose/脚本齐全
